  - **作成**：元の SWE-bench は、実在の GitHub の issue と、それを直した PR から作る。各件は、PR が足した「直る前は失敗し、直ると通るテスト（FAIL_TO_PASS）」と、「直る前後で通り続けるべきテスト（PASS_TO_PASS）」を持つ。モデルには issue の文章とコードだけを見せ、テストは見せない。修正を当てて 2 種類のテストがすべて通れば「解決」。
  - **検証**（Verified）：OpenAI が SWE-bench の著者と共同で作った。Python に詳しいソフトウェア開発者 **93 人**が、元のテストセットから無作為の **1,699 件**に注釈を付けた。注釈者は、その分野のコードに詳しいとは限らない。先にエンジニアが 50 件へ高い確信でラベルを付けて導入用のテストにし、合格した人だけが参加した。
    - 各件は**別々の 3 人**が付け、**いちばん深刻なラベルを採用**した（1 人でも問題を指摘したら除外）。
    - 基準は 2 つで、各 0〜3 の 4 段階（2 以上で除外）。「課題文が十分に特定されているか」と「FAIL_TO_PASS のテストが、正しい解法を落とさないか」。ほかに自由記述欄と、解くのにかかる時間の見積もり（難易度）がある。難易度は除外には使っていない。
    - 結果：課題文の不足が 38.3%、テストの不備が 61.1%（重なりがある）。合わせて **68.3% を除外**した。OpenAI は、除外が行きすぎている可能性が高いが、残った件の信頼は高まる、と書いている。
    - 残す 500 件は、1〜4 時間と 4 時間超の課題をできるだけ残し、あとは無作為に選んだ。難易度は 15 分未満が 196 件、1 時間超が 45 件。
  - **その後**（2026-02-23）：OpenAI は Verified のスコア報告をやめた。理由は 2 つ。(1) OpenAI o3 が 64 回の独立した実行で一貫して解けなかった 138 件を、各件 6 人以上のエンジニアで監査したところ、**59.4%** に重大な問題があった（実装の細部を強いるテスト 35.5%、課題文にない機能まで調べるテスト 18.8%）。(2) テストした最先端のモデルがすべて、正解のパッチか課題文の具体的な内容のどちらかを、そのまま再現できた（学習データに入っている疑い）。後継として SWE-bench Pro を勧めている。

- 気づき・疑問：
  - 5 件を読んで、難しさは直す行数ではなかった。直すのは 1 行のものもあるが（astropy-12907、django-17087）、原因を探すことと、何が正しい動作かを決めることが難しいと感じた。例えば scikit-learn-9288 は、期待（`n_jobs` によらず結果が同じになるはず）は issue に書いてあるが、原因（単一スレッドと並列で、乱数の種の作り方が違う）は書かれておらず、コードを読んで探すことになる。django-13568 は、issue の筆者自身が「バグかどうか分からない」と書いている。ただし私は正解のパッチを見たうえで読んだので、「自分なら解けるか」は甘く見ている。
  - sympy-19495 の issue は、「変だ」と言うだけでなく、おかしい出力と、同じ式を `xreplace` や `subs(…, simultaneous=True)` で置き換えると正しい形になることを並べて示している。課題文だけで直す方向が決まる、仕様が明確な例だと感じた。一方、OpenAI の記事の例（scikit-learn-14520）は、issue は「`copy` 引数が使われていないが、見落としか」と尋ねるだけなのに、テストは非推奨の警告の文面まで完全一致で求め、記事は「ほぼ不可能」としている。モデルにテストは見えないので、課題文にない条件が採点に入ると、正しい修正でも落ちる。今日の rubric で「まだ決めていないこと」を放っておくと LLM の判定が割れる（unsure になる）のと、同じ構造だと思った。
  - Verified は、人の検証を厚くして（3 人・最も厳しいラベル）評価セットの質を上げた例だった。それでも 2026 年の監査で、難しい 138 件の 59.4% に欠陥が見つかり、公開のリポジトリ由来なので学習データへの混入も起きた。講義の「基準は変わっていくので最初から完璧にしない」「評価セットも更新する」「有名なベンチマークにも誤りがある」と重なる。人の検証をしても、一度で終わらない。
  - 今日の演習は、採点を LLM に任せるので「採点器を人が確かめる」。Verified はコードで採点するが、そのテスト自体を人が確かめていた。コードで確かめられるものはコードで、という講義の話は正しいが、コードの採点も、テストが悪いと不当に落とす。採点の主体が人・LLM・コードのどれでも、基準（テスト）を人が見直す工程がいる。
  - 疑問：3 人の注釈者の一致率が、記事の本文には書かれていなかった。人同士がどれくらい割れたかが分かれば、今日の「人同士でも割れる」の大きさと比べられる。また、今日の 10 件は 1 件の違いで一致率が 10 ポイント動くが、500 件の Verified でも、難しい 138 件を選んで監査すると結果が大きく変わる。件数だけでなく、どの件を調べるかで見え方が変わることも気になった。
